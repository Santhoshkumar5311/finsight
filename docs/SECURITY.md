# Security implementation and deployment requirements

This is a runnable development implementation. It is not a security certification or a claim that an unconfigured environment satisfies all five layers.

## Threat boundaries

- A model cannot request money movement: no corresponding tool exists. Tool outputs omit secrets; banking writes belong only to the trusted Plaid ingestion code. `finsight_agent` has SELECT on banking records and no INSERT/UPDATE/DELETE privileges there. The application mediator recomputes and signs metrics rather than accepting model-provided numbers.
- Each HTTP and Socket.io connection derives its owner from a verified JWT, never a request-body user ID. Live connections are closed periodically to bound session reuse. Refreshing credentials requires a reconnect.
- Owner-scoped SQL predicates are used in addition to row-level policies. Database migration credentials are trusted infrastructure credentials, not mobile/web credentials. The migration revokes client-role access to credentials, inbox and audit. Never distribute a database URL or Supabase service-role key to a client.
- Signed webhooks require ES256, a Plaid-provided verification key, a recent `iat`, and a constant-time raw-body SHA-256 match. Inbox IDs prevent processing the same signature twice. Repeated deliveries remain safe because transactions are upserted by stable tokens.
- Audio is streamed through an authenticated endpoint, never a public S3 URL. The backend checks owner and diary ID. S3 credentials are resolved from the standard AWS provider chain; use an IAM role in production.
- Web push endpoints are HTTPS and limited to supported browser push-provider hostnames. Request rate limits are per process; edge WAF limits provide fleet-level protection. Add a shared Redis limiter for fine-grained cross-replica user quotas.
- API logs contain action/resource metadata and error classes, not tokens or transaction payloads. The SQL audit table must be insert-only for runtime identities and shipped to an immutable audit sink.

## Outstanding release gates

1. Apply and exercise the migration in PostgreSQL/Supabase; verify cross-tenant RLS with two real users and a restricted runtime role. The actual migration and RLS/agent grants passed embedded PostgreSQL (PGlite + pgvector) tests; hosted PostgreSQL/Supabase deployment and pool behavior remain untested.
2. Run Plaid Sandbox Link, initial/historical webhooks, mutation pagination, reconnect, revocation, replay and item-error scenarios. Verify USD exclusions are suitable for intended banks.
3. Run on physical iOS and Android devices: OAuth deep links, TOTP, biometrics, keychain persistence, pin mismatch/rotation, foreground/background lock, audio permission/re-recording and notification scheduling.
4. Deploy TLS/WAF/private storage, apply IAM and service DB grants, configure encrypted queue/cache storage, rotate keys, and test backup restoration. Terraform is a security foundation for an existing VPC/application load balancer; it does not deploy application compute or all Supabase services.
5. Validate PII detection and remote mobile push; add immutable audit export, role-isolated worker deployment, and deployment-specific CSP nonces before accepting real customer data.
6. Run external-service integration, concurrency, outage/recovery and load tests. Confirm the requested two-second webhook-to-dashboard and one-second LLM SLOs under representative load; do not infer them from local demo timings.
